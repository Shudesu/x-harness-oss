## Activation / upgrade procedure (not executed remotely)

1. Back up the target D1 database and its configuration using the owner's approved account/wrapper. Inspect `sqlite_master`, table columns and existing migration history. Confirm the actual deployment/repository is x-harness-oss, not the THC control plane or tenant repository.
2. For a new empty database only, apply the migrations under `packages/db/bootstrap` using `wrangler d1 migrations apply`. `000-baseline.sql` contains the pre-019 schema; `019` is identical to the additive legacy upgrade. Never apply baseline 000 over a populated DB.
3. For an existing database already at the schema represented by migrations 001–018, apply only `packages/db/migrations/019-security-cost-ai.sql` after schema review. This keeps original columns/data and preserves gate delivery methods. Do not apply old ALTER files blindly; record adoption in the environment's migration history. Invalid legacy schedule values need operator review; they are not guessed into dates.
4. Configure stable `ENCRYPTION_KEY` (32 random bytes, base64), existing `API_KEY`, exact comma-separated `ADMIN_ORIGIN`, and correct `WORKER_URL`. Never rotate the encryption key by overwriting it while ciphertext still depends on it. The setup wizard checks for an existing key and does not replace it on a rerun.
5. Run checks and a Worker dry-run before the separately authorized deployment. Set `XAI_API_KEY` only if using Grok. `XAI_MODEL` defaults to grok-4.3 and `XAI_MONTHLY_BUDGET_USD` to 5. Set application X budget in Settings; default 50. Set provider-side caps as well: one in-flight request or concurrent calls can cross an application threshold, and timed-out requests may still be billable.
6. With the deployed admin endpoint available, run `node scripts/migrate-secrets.mjs` with `X_HARNESS_API_URL` and `X_HARNESS_API_KEY` in the environment for counts only. `--apply` upgrades at most 100 rows per column. Repeat the count check and batches until pending counts are zero. No keys are printed. Existing staff keys are also upgraded during successful login. Retain the encryption key in secure backup with DB backups.
7. OAuth2: set `X_OAUTH_CLIENT_ID` and optional confidential-client `X_OAUTH_CLIENT_SECRET`; register the exact callback `<WORKER_URL>/api/x/oauth/callback` in X. Use Settings to authorize. This requires an actual user OAuth test before production acceptance. OAuth1 registrations continue to work.
8. Public LIFF integrations must send `gateId` to `/api/users/search`. Public `/api/followers/search` and `/repliers` are no longer available; use the gate-scoped search and eligibility-only verify API. This is an intentional security boundary and must be coordinated with the caller before rollout.
9. Enable daily digest explicitly in Settings after reviewing the budget. Generated drafts require existing approval/posting actions. For an ambiguous scheduled send, inspect X and the claim before deciding whether to restore it; never delete a claim automatically after a timeout.
